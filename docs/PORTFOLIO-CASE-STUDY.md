# Portfolio Case Study: AI Freelance Intelligence Pipeline

## Problem

Senior freelance engineers waste 2–4 hours daily on a broken discovery process. Upwork's email alert system delivers incomplete data — no client spending history, no average hourly rate paid, no active competition count. Engineers manually evaluate dozens of jobs to find ones worth the 30–60 minute investment to write a tailored proposal.

The result is a poor signal-to-noise ratio. The average freelancer applies to 15 jobs per contract won. The root cause is decision-making without evidence.

## Architecture

The system is built around a domain-driven architecture with clear separation of concerns:

```
domain/       → Core types and interfaces
application/  → Pipeline orchestration, decision engine, analytics
ai/           → Agents, routing, RAG, telemetry
integrations/ → MCP client (Upwork)
workers/      → IMAP ingestion worker
app/          → Next.js dashboard
```

The key design principle: **the domain layer has no AI dependencies**. Agent outputs are typed domain objects. The pipeline doesn't care which model produced them.

## AI Design

### Agent Decomposition
Rather than a monolithic prompt, the system uses 8 specialized agents organized in a parallel-then-sequential flow:

- Parallel: Job Intelligence, Client Intelligence, Competition analysis run concurrently
- Sequential: FreelancerFit, Economic consume tier-1 outputs → Decision Engine synthesizes all

Each agent boundary was justified by whether the reasoning domain could be independently optimized. Agents that share too much reasoning scope were merged.

### Provider Abstraction
The `AIProvider` interface abstracts away the specific SDK calls. Changing from OpenAI to Gemini for any agent requires only a router config change — no agent code modifications. This was validated by the cross-provider fallback implementation, which proved the abstraction held under failure conditions.

### Structured Outputs
All agents use Zod schemas for output validation. A failed schema parse triggers retry on the next model in the fallback chain — not a crash. This is different from most AI tutorials where `JSON.parse` is called on raw completions and hoped to work.

### RAG Without a Vector Database
The knowledge base uses in-memory cosine similarity over pre-computed embeddings stored as JSON in SQLite. The decision to avoid pgvector or a separate vector store was based on scale: the knowledge base contains tens to low hundreds of items, making a separate database introduce infrastructure complexity without performance benefit.

The anti-hallucination loop is the more important design choice: the `ClaimVerificationAgent` explicitly rejects and triggers regeneration of any proposal containing claims not traceable to the provided evidence.

## Engineering Challenges

### 1. Anti-Hallucination Under Generation Pressure
LLMs will hallucinate experience under pressure to produce a compelling proposal. The naive solution (system prompt instructions) is probabilistic. The implemented solution (verification loop with deterministic rejection) is not — it provides a hard guarantee.

**Challenge**: The verification agent itself could be manipulated by a sufficiently confident hallucination. Mitigation: the verifier compares claims against the evidence *as passed in context*, not as generated by the drafter.

### 2. Cost/Quality Tradeoff in Multi-Agent Pipelines
Running 8 agents per opportunity at GPT-4o rates would cost ~$0.50–$1.00 per opportunity. At scale (50 opportunities/day), that's $15,000/year just for inference.

The solution is the `ModelRouter`: route parsing to `gpt-4o-mini` (~$0.002/k tokens) and reserve `gpt-4o` (~$0.01/k tokens) only for reasoning tasks. This reduces per-opportunity cost by ~60–70% with minimal quality degradation on extraction tasks.

### 3. Data Asymmetry and MCP Integration
Email alerts omit critical decision signals. Implementing a direct Upwork API integration would require OAuth setup, token management, and endpoint-specific code. The MCP integration proved simpler: the official Upwork MCP server handles authentication, and the client only calls well-defined tool names.

The tradeoff: each MCP call spawns a subprocess (via `mcp-remote`). In production, this would require connection pooling. A 10-second timeout prevents this from stalling the pipeline.

### 4. Observable but Not Intrusive Telemetry
Telemetry (token counts, latency, cost, model used) is persisted via fire-and-forget calls — never on the critical path. A telemetry failure must not fail a pipeline run. The implementation uses `.catch(console.error)` on the Prisma upsert call, deliberately preventing any telemetry error from propagating to the caller.

## Tradeoffs

| Decision | Alternative | Reason for Choice |
|---|---|---|
| SQLite | PostgreSQL/Neon | Single-machine tool, zero infrastructure |
| In-memory cosine similarity | pgvector | Portfolio < 200 items; infra overhead unjustified |
| 8 specialized agents | 1 monolithic prompt | Testability, cost routing, independent optimization |
| Verification loop | Instruction-only hallucination control | Probabilistic vs. deterministic guarantee |
| MCP | Direct Upwork REST API | Official integration, token management handled externally |

## Evaluation

The system includes a benchmark evaluation framework with:
- 30 labeled test cases covering 6 categories
- MetricsEngine calculating Precision, Recall, F1, FPR/FNR
- A golden dataset generator that promotes human-calibrated real outcomes to evaluation data

Run `npm run evaluate` to measure current system performance against the benchmark.

## Results

The system has been evaluated against a synthetic benchmark dataset. Real-world outcome data (Apply → Interview → Contract rates) will populate via the Phase 7 feedback loop as the system is used in production.

Key systemic properties:
- **Zero hallucinated claims** in final proposals (ClaimVerificationAgent guarantee)
- **Cross-provider resilience**: any single-provider outage triggers automatic fallback
- **Full execution traceability**: every agent run logged with model, tokens, cost, latency
- **Calibration loop**: AI scores can be correlated against real outcomes via FeedbackManager

## Lessons Learned

1. **Deterministic guardrails are essential before LLM calls**. Checking basic conditions (is client blacklisted? is budget below threshold?) with deterministic logic before invoking an LLM saves tokens and prevents edge-case failures.

2. **Evaluation should be built before the system is complete**. The benchmark dataset forced us to define what "correct" means precisely — which clarified ambiguous cases that would have been resolved inconsistently by the agents.

3. **Provider abstraction pays for itself quickly**. Once the fallback mechanism was in place, adding cross-provider resilience required no changes to any agent — only changes to the router.

4. **In-memory retrieval is often sufficient**. The RAG implementation works without any vector database infrastructure. The impulse to reach for specialized infrastructure should be resisted until scale actually demands it.
